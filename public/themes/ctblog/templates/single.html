先说结论：不是微服务不好，是我一个人扛不动它的运维成本。如果你的团队是 3 到 5 个人，且没有专门的平台工程，那这篇文章里的坑，你大概率也会踩。

为什么要拆

2024 年底，我那个产品开始出现「改一处、崩一片」的情况。支付、内容、通知混在同一个进程里，一次上线要等 20 分钟的测试，任何一个小改动都得全量发布。当时的判断很直觉：拆开就能独立发布、独立伸缩。

拆分的隐性成本

拆是拆开了，但成本并不在你预期的地方。真正吃掉时间的是下面这三样。

部署与调用链

7 个服务意味着 7 套健康检查、7 份配置、7 条日志流。一个下单请求要穿过网关、账户、库存、通知四个服务。出问题时，我需要在四个日志面板之间来回跳，才能拼出一次完整的失败路径。

分布式系统里，你会用一生去追一个本可以在本地断点就能解决的问题。

跨服务的数据一致性

原本一个事务能搞定的事，现在要引入消息队列和补偿逻辑。下面这段是当时的「退款」流程，为了跨服务一致性写了近 40 行状态机，而它在单体里只是两行 SQL：

// 分布式版：退款要先冻结、再通知、最后对账
await reserve.refund(orderId)      // 服务 A
await ledger.credit(orderId)       // 服务 B（可能失败）
await notify.refunded(orderId)     // 服务 C（可重试）
// 任何一步失败 → 补偿任务排队处理 → 第二个 bug 诞生

什么时候单体真的不够用

  • 团队规模：多个团队并行开发、需要独立发布节奏时，模块化的边界比部署边界更重要。
  • 伸缩差异：某个模块的负载比其余高两个数量级，需要单独扩容。
  • 故障隔离：一条业务线的崩溃不能拖垮全站，且你有专门的 SRE 兜底。

如果你一条都不满足，那「微服务」带给你的主要是简历上的名词，而不是产品上的收益。

我们怎么退回来的

没有大张旗鼓地重构。做法是：先把服务间的调用改成进程内的模块接口，但保留原有边界；一个模块一个模块地并回去，每并一个跑一周观察。三个月后，进程从 7 个变成 2 个——一个 Web、一个异步 Worker。

关键在于，我们保留的是模块边界，丢掉的只是网络边界。代码结构没有变乱，反而因为少了序列化和超时处理更干净了。

结论

单体的真正问题从来不是「单体」，而是没有边界的单体。用模块把内部切清楚，先从单体开始；等团队和规模真的撑不住，再把边界升级成服务。到那时你会发现，前面省下的每一次运维，都在为你要拆的那一天攒底气。
